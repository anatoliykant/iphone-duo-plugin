# Проверка макетов iPhone Duo по Apple HIG

Инструкция для дизайнера. Claude Code или Codex читает твой файл в Figma, сверяет каждый экран с гайдлайнами
Apple — общими iOS-правилами и 29 правилами под складной iPhone — и отдаёт список находок с цитатой
из гайда и вердиктом «можно в разработку» или «нет».

Нужен плагин `iphone-duo`, скилл `hig-design-review`.

---

## 1. Настройка — один раз, минут пятнадцать

### 1.1. Поставить плагин

В терминале, из любой папки. Для Claude Code:

```bash
claude plugin marketplace add anatoliykant/iphone-duo-plugin
claude plugin install iphone-duo@anatoliykant-plugins
```

Для Codex:

```bash
codex plugin marketplace add anatoliykant/iphone-duo-plugin
codex plugin add iphone-duo@anatoliykant-plugins
```

После установки открой новую сессию. Установка из локальной папки и вариант только со скиллами
описаны в [README](../README.md#install).

### 1.2. Подключить Figma

Оба агента читают Figma через MCP. Для сервера `mcp-figma` выбери команду своего агента:

```bash
# Claude Code
claude mcp add figma -- npx -y mcp-figma mcp
# Codex
codex mcp add figma -- npx -y mcp-figma mcp
```

Нужен личный токен Figma: <https://www.figma.com/settings> → вкладка **Security** → **Personal
access tokens** → **Generate new token**.

- Достаточно прав **File content: read-only**.
- Хочешь, чтобы агент умел оставлять комментарии в файле — добавь **Comments: write**.
- Токен показывают один раз, скопируй сразу.

Настрой токен по инструкции выбранного Figma MCP-сервера. Если Figma уже подключена в твоём
агенте, используй существующее подключение; доступные измерения зависят от его инструментов.

### 1.3. Проверить, что всё завелось

Запусти `claude` в любой папке и набери `/iphone-duo:hig-design-review`. Если команда есть в
списке — готово.

В Codex выбери `$iphone-duo:hig-design-review` через список `$` и отправь `--help`.
Если устанавливались только скиллы, имя короче: `$hig-design-review`.

## 2. Что нарисовать до ревью

iPhone Duo — это два экрана, и проверять нечего, пока в файле только «телефонные» фреймы 390–430 pt.
Ревью первым делом ищет фреймы вот таких размеров и по ним определяет, что за экран перед ним.
**Имена фреймов он игнорирует — смотрит на реальный размер.**

| Размер фрейма | Что это | Бары |
|---|---|---|
| 466 × 678 | Внешний экран, портрет — закрытое устройство | вертикальные, сбоку |
| 678 × 466 | Внешний экран, ландшафт | вертикальные |
| 626 × 890 | Внутренний экран, портрет | **горизонтальные** — единственный случай |
| 890 × 626 | Внутренний экран, ландшафт — поза «книга» | вертикальные |
| 313 × 890 | Половина Split View: два приложения рядом | вертикальные, по внешнему краю |

Размеры в поинтах выведены из пиксельных спецификаций Apple (@3x) — сама Apple их в поинтах не
публикует. В отчёте они всегда помечены как расчётные.

**Минимум на экран — два фрейма: внешний и внутренний.** Если экран должен работать в сложенном
виде, добавь ещё один фрейм для сложенного состояния: на внутреннем ландшафтном экране линия сгиба
вертикальная и проходит примерно по x = 445, на портретном — горизонтальная примерно по y = 445.

> **Готовые дизайн-киты**
>
> Apple опубликовала киты iPhone Duo для Figma и Sketch: <https://developer.apple.com/design/resources/>. Рамки, бары и safe area там уже правильных размеров — быстрее, чем размечать вручную.

> **Если макет пока в Claude Design**
>
> Выгрузи артборды в PNG и отдай файлы агенту вместо ссылки на Figma. Ревью пройдёт в режиме
> «visual-only»: композицию, бары, сгиб и иерархию он проверит, а замеры — размеры шрифтов,
> тап-таргеты, контраст — пометит как «не проверить по экспорту».

## 3. Как запустить

Скопируй ссылку на фрейм в Figma (правый клик по фрейму → **Copy link to selection**) и напиши в
Claude Code:

```
/iphone-duo:hig-design-review https://www.figma.com/design/ABC123/Название?node-id=12-345

Проверь эти экраны на соответствие HIG для iPhone Duo.
```

В Codex тот же запрос начинается так:

```text
$iphone-duo:hig-design-review https://www.figma.com/design/ABC123/Название?node-id=12-345

Проверь эти экраны на соответствие HIG для iPhone Duo.
```

Можно и без явного вызова — просто дать ссылку и попросить проверить макет по гайдлайнам Apple: скилл
подхватится сам. Ссылка на весь файл тоже подойдёт — тогда агент покажет список экранов и спросит,
какие брать, если их больше десятка.

Он сам обойдёт все страницы файла: макеты под Duo часто лежат на отдельной странице, и без этого он
бы сказал «внутреннего экрана нет».

## 4. Что придёт в ответ

Отчёт: строка на находку — экран, id ноды, что не так, цитата из гайда и чем это чинится. Плюс
вердикт по каждому экрану и по набору:

- **Ready** — можно отдавать в разработку.
- **Ready with notes** — можно, но список замечаний уходит разработчику как ограничения («собирать
  системным тулбаром, хотя в макете нарисован свой»).
- **Not ready** — есть блокер либо три и больше обязательных правок на одном экране.

Уровни находок:

| Уровень | Что значит |
|---|---|
| **BLOCKER** | Система это не исправит на лету |
| **MUST-FIX** | Нарушено прямое правило Apple |
| **SHOULD** | Рекомендация, система может частично компенсировать |
| **NOTE** | Наблюдение, не нарушение |

Отдельным блоком идёт «что по макету не проверить» — анимация, хаптика, порядок VoiceOver, поведение
при реальном сгибе: это уже ревью кода.

Правило без цитаты из гайда автоматически понижается до SHOULD и помечается «суждение ревьюера» —
чтобы «Apple так сказала» нельзя было предъявить там, где Apple ничего не говорила.

> **Комментарии в Figma**
>
> По умолчанию агент ничего в файле не трогает. Если попросишь — разложит блокеры и обязательные
> правки комментариями по нодам с префиксом `[HIG review]`. Только после того, как ты увидела отчёт
> и подтвердила. Сам макет он не правит никогда.

## 5. Что ломается чаще всего

Семь вещей, из-за которых макет под Duo обычно уезжает в «Not ready». Проще проверить самой до
запуска.

| Уровень | Находка | Почему |
|---|---|---|
| BLOCKER | Нарисован только внешний экран | Внутренний — это *regular × regular*, впервые на iPhone. Растянутый внешний макет там не работает |
| BLOCKER | Таб-бар снизу, навбар сверху — на внешнем экране | Система сама уносит бары на боковую грань: экран шире и ниже обычного, вертикаль дорога. Свой бар поверх скрытого системного отключает всё поведение разом |
| BLOCKER | Кнопка, поле или лицо на линии сгиба | Сгиб физически есть в любой позе. Фон и скроллящийся контент через него идут, интерактив и смысловые элементы — нет |
| MUST-FIX | Нечётное число колонок в сетке на внутреннем экране | Сгиб делит экран пополам: при чётном числе колонки делятся чисто, при трёх средняя попадает на линию |
| MUST-FIX | Текстовые кнопки в барах | Элемент с текстом остаётся в горизонтальном баре и съедает место. Нужны символ + название; счётчик — бейджем, не строкой «Входящие 7» |
| SHOULD | Отдельный макет под позу — «книга», «стол», «палатка» | Дизайн делается под два класса размера, а не под позы. Иначе поз получается пять, и каждая живёт своей жизнью |
| SHOULD | Между позами экран перестраивается до неузнаваемости | Переход человек видит целиком. Apple прямо называет «дизайн под каждую позу» главной ошибкой, которую уже встречала |

## 6. Дальше

Если по находке возник вопрос «а как это вообще собирается» — скажи разработчику, что в том же
плагине есть второй скилл, `iphone-duo`: он отвечает за реализацию и знает, какой системный компонент
закрывает каждое правило. Ревью макета останавливается на «что не так и почему».

Гайд, по которому идёт сверка:
[Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo).
Агент берёт его с сайта при каждом запуске, а не по памяти — страница ещё будет меняться.
